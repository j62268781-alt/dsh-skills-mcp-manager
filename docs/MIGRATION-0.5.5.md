# 0.5.5 升级与迁移

> 面向**从 0.5.4 升级**的用户与维护者。这一版包含**破坏性变更**：插件身份、MCP 配置的
> 存储方式、技能的落盘位置都变了。绝大多数情况**自动完成**，但有三处需要人确认。

## 一分钟版

| 你担心的事 | 实际情况 |
|---|---|
| 我的 MCP 服务器会丢吗 | **不会。** 自动迁移，连接参数原样保留 |
| 我的技能会丢吗 | **不会。** 文件原地不动，只是归属清单换了文件名 |
| 需要手动改配置文件吗 | **不需要。** 启动时自动迁移，迁移前自动备份 |
| 需要重启吗 | **需要，且只需要一次。** Host 侧改动无法热加载 |
| 想回退怎么办 | 见文末「回退」。0.5.4 的配置会被完整保留 |

## 一、为什么这版是破坏性的

三个改动都动了「数据存在哪里」，而不只是代码：

1. **插件身份改名**：`skills-mcp-panel` → `dsh-skills-mcp-manager`
2. **MCP 配置单一来源**：项目级从插件自己的 `config.servers[]` 改为 profile 行（`scope` 即档位）
3. **MCP 行操作换传输**：settings 队列 → `POST /<插件名>/rows`（HTTP）

不做迁移的后果分别是：面板认不出自己的配置行（**列表全空**）、项目级服务器**连不上**、
命令**没有响应**。所以迁移不是「顺手做的优化」，是这三个改动能成立的前提。

## 二、迁移项逐条说明

### 1. 插件身份：行 id 与 settings 命名空间

**改了什么**：profile patch 里的行 id、settings 命名空间、运行时路由、日志前缀、
诊断文件名，全部统一成 `dsh-skills-mcp-manager`。

**为什么必须迁**：面板通过行 id 找到自己在 patch 里的位置。id 不匹配时它找不到那一行，
于是**所有 MCP 配置都看不到** —— 表现是「升级后列表空了」，而配置文件其实完好。

**自动迁移**（`src/patch/apply.js` 的 `migratePanelConfig`，启动后由 `publish` 触发一次）：

- 遍历 patch 的顶层行与 `insert:` 子行，把 id 为旧名的改成新名；
- 顺带删除三个已废弃的运行时字段（`serverTools` / `serverToolsError` / `serverStatus`）——
  它们占旧配置的 34.6%，且每 5 秒重写一次；
- **原样保留**其余所有键（连接参数、技能、过滤规则、工作区）；
- 写盘前先备份，全程持文件锁；
- 幂等：无事可做时返回 `0`，不会反复写盘。

**顺序很关键**：迁移必须早于第一次投影写入，否则新命名空间的行会先落地，之后旧行再被改名，
同一个插件就出现**两行** —— 配置被读两遍。这一条有回归测试盯着。

### 2. 项目级 MCP：从 `config.servers[]` 到带 `scope` 的 profile 行

**改了什么**：项目级服务器以前存在插件自己的 settings 字段里，由插件在运行时挂载；
现在和全局服务器一样是 `mcp-client` 行，`config.scope` 标明它属于哪个工作区。

**为什么改**：两档曾经是两种东西（一份在 patch、一份在插件字段），于是要合并两个数组才能
显示一个列表，而且**无作用域**读注册表根本看不到项目级的工具 —— 每台项目服务器都报 0 个工具。
统一成行之后，「档位」只是行的一个字段，作用域读取才有唯一的依据。

**自动迁移**（`migrateServerEntries`）：

- 每条 `config.servers[]` 条目转成一条 `mcp-client` 行，**包括全局条目** ——
  只转一半会让两个来源继续并存；
- 转换复用 `applyRowOp` 的 add 路径，所以迁移出来的行与手工添加的**字节一致**；
- 已有同名行时**不覆盖**（`migrated === 0`），重复运行是安全的；
- 项目行写 `disabled: true`：Loader 不该实例化它，由本插件挂进目标 agent 的 ctx。
  **`disabled` 在项目档的含义是「Loader 别连」而不是「用户关掉了它」** ——
  用户开关看的是 `enabled`。这两者混淆过，值得单独记一笔。

### 3. 行命令：settings 队列 → HTTP

**改了什么**：面板对 profile 行的增删改，从「写进 settings 队列，Host 轮询取走」改为
直接 `POST /dsh-skills-mcp-manager/rows`。

**为什么改**：写 `cordis.patch.yml` 实测只要 **1–5ms**，而队列通道要让用户等 **2–4 秒**：
500ms 排空轮询 + 一段固定的 1200ms 死等（用来岔开两次 HMR 写入）+ Loader 重载 +
面板自己 700/1500ms 的轮询。用户点完只看到转圈，删除的卡片还留在屏幕上。

**兼容性**：**设置队列保留为回退通道**，仍在排空。所以：

- 新面板 + 新 Host → 走 HTTP（快路径）；
- 旧面板 + 新 Host → 走队列（仍然可用）；
- 新面板 + 旧 Host → 请求 404/405，自动回退队列。

三条路都有测试，**不需要用户做任何事**。

### 4. 技能：「区域」与落盘根

**改了什么**：技能条目的「区域」现在写进配置（`id: dsh | agents`），面板提供**四个**真实路径：

| 区域 | 路径 |
|---|---|
| 全局 · dsh | `$DSH_HOME/skills` |
| 全局 · agents | `~/.agents/skills`（可用 `DSH_AGENTS_HOME` 覆盖） |
| 项目级 · dsh | `<工作区>/.dsh/skills` |
| 项目级 · agents | `<工作区>/.agents/skills` |

**为什么改**：DSH 的 provider **四个根都读**，但 `config.skills[]` 之前不记录落盘根，
而 reconcile 把根写死。于是写到 `~/.agents/skills` 的文件会在下一轮被**删除并在默认根重写**，
没有任何报错 —— 用户看到自己刚建的技能「不见了」或「跑到别处」。

**迁移**：`id` 缺省为 `dsh`，所以**旧条目语义完全不变**（它们本来就写在 dsh 根）。
编辑条目时若草稿没带 `id`，从原条目继承 —— 改文字不该搬动文件。

**技能归属清单换名**：`skills-mcp-panel.state.json` → `dsh-skills-mcp-manager.state.json`。
首次读取时若新文件不存在则导入旧文件，并用 `{ flag: 'wx' }` 写入（**绝不覆盖**另一个实例
刚创建的文件）。

### 5. 连接与重连默认值改为显式

**改了什么**：`reconnect.*` 与 `toolCallTimeoutMs` 的默认值以前**省略不写**，由 MCP 客户端补；
现在表单预填、落库也写显式值。`failOnStartupError` 例外（`false` 与「键不存在」等价）。

**为什么改**：表单显示「未设置」而 500 其实在生效，且那个值住在 `dsh-mcp-client` 里 ——
用户要读别人的源码才知道这一行会怎么重连。

**迁移**：旧条目里没有这些键，读回时按默认值显示，下次保存时写成显式值。**无需手动处理**。

### 6. 项目级挂载丢失 env / headers（issue #2）

**改了什么**：`env` 与 `headers` 的解析改为接受两种形状（对象 / `KEY=VALUE` 文本行）。

**为什么改**：`serverRows()` 产出的已经是**对象**，而 `mount.js` 对它调 `parseEnv()` ——
后者期望文本行，`String(object)` 是 `"[object Object]"`，没有 `=`，于是每行都被跳过、
返回 `{}`。结果是项目级 stdio 行的 `JAVA_HOME`、`GHIDRA_INSTALL_DIR` **静默消失**，
而 http 行的 **Authorization 静默丢失**（表现为一台带着凭据的服务器显示「需要授权」）。

**迁移**：无需动作。升级后**可以撤掉「启动壳」绕行**（把行的 `command` 指回真程序）。

### 7. 项目行状态问错了权威源（issue #3）

**改了什么**：`connected` 对两档一致地信任「此作用域下该服务器注册了工具」。

**为什么改**：`connected` 只在全局档信任 `toolCount`，项目行只能靠 probe；而 probe 问的是
DSH 注册表，项目行按设计**不注册**进去，必然得到 `unavailable in this agent's scope`，
再按重试预算推导成「已放弃重试」。于是一台**工作完全正常**的服务器长期显示故障，
用户会去反复改配置。实际危害是误导，不是功能损坏。

**迁移**：无需动作，纯展示层修复。

## 三、升级步骤

1. **升级包**：`dsh plugin --profile desktop add <0.5.5 的 tgz 或 npm 包>`
2. **重启一次 DSH**（Host 侧改动无法热加载；这也是迁移生效的时刻）
3. 打开 **设置 → Skills & MCP**，确认：
   - MCP 列表里有你原有的服务器（含项目级的）
   - 项目级卡片的标签显示**工作区名**
   - 技能列表里有你的技能

首次启动会自动写备份（见下）。迁移是幂等的，重启多次不会重复改动。

## 四、自动备份

每次写 profile patch 前，插件把它复制到：

```
$DSH_HOME/dsh-skills-mcp-manager.backups/cordis.patch.yml.bak
```

**这是一个滚动文件（只保留最近一次）**，且**没有自动恢复路径** —— 它的用途是撤销
*刚刚那次*操作。需要长期历史请依赖 git 或 DSH 自己的 profile 备份。

> 已知取舍：0.5.4 及更早的旧备份目录 `skills-mcp-panel.backups/` **不会**被删除或迁移，
> 原地留存。它不影响功能，可以自行清理。

## 五、回退

1. 装回 0.5.4：`dsh plugin --profile desktop add @j62268781-alt/dsh-skills-mcp-manager@0.5.4`
2. 重启 DSH
3. **如果面板列表是空的**，说明插件认不出新 id 的行 —— 用备份或 git 把
   `cordis.patch.yml` 里的行 id 从 `dsh-skills-mcp-manager` 改回 `skills-mcp-panel`：
   `cp $DSH_HOME/dsh-skills-mcp-manager.backups/cordis.patch.yml.bak <profile>/cordis.patch.yml`

回退**不会**丢数据：迁移只改行 id 与三个废弃字段，连接参数、技能、过滤规则都原样保留。
反过来说：迁移后新面板写的显式默认值（`reconnect.*` / `toolCallTimeoutMs`）在旧版里会被
忽略 —— 旧版省略这些键时行为相同，所以无影响。
